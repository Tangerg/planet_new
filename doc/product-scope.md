# Planet 产品能力边界与 Provider 职责

本文定义 Planet 的核心职责范围:哪些能力要做,哪些能力不做,以及多 provider 下能力应该如何分层和演进。它是产品取舍文档,不是具体 API 调研;API 生态与技术接入细节见 `doc/provider-plan.md`。

---

## 1. 产品定位

Planet 是一个多 provider 的沉浸式桌面音乐播放器。

核心目标是把「找歌、看专辑/歌单/艺术家、播放、歌词、评论、个人音乐库」这一套流媒体音乐体验做到克制、稳定、好看,而不是复刻官方客户端的所有功能。

设计取舍:

- 少即是多:只承载音乐播放链路里的高价值能力。
- 多 provider:当前先以 NCM(网易云音乐)为主,后续接 QQ 音乐与本地播放 provider。
- 能力诚实:provider 没有、数据不完整、接口不稳定时,UI 只展示真实可用的能力。
- 领域优先:UI 不认识具体平台接口,只认识统一的音乐领域模型和能力。
- 不做大杂烩:不为了“接口里有”就把签到、任务、社交、播客、广播等低相关能力塞进产品。

---

## 2. Provider 策略

Provider 是外部音乐数据源的防腐层。它把 NCM、QQ、本地文件等不同来源映射成 Planet 自己的领域模型。

基本原则:

- UI 和应用服务只依赖 Catalog / Playback / Auth / User Library 等最小领域端口,不直接调用某个平台 API。
- 每个 provider 显式声明自己支持的能力;不支持的能力在 UI 上隐藏入口或展示诚实空态。
- provider 返回的字段必须先归一化成 domain model,平台字段名、接口 shape、异常码不能泄漏到 UI。
- 同一能力在不同 provider 上可能有差异,差异通过 capability 和空值表达,不要在 UI 里写平台分支。
- 能力命名按产品含义来,不要照搬平台文案。例如艺术家热门歌曲应叫 `Hot`,不叫 `Top 50`,因为接口经常拿不到 50 首。

Provider 分阶段定位:

| Provider               | 定位              | 当前/目标职责                                                                 |
| ---------------------- | ----------------- | ----------------------------------------------------------------------------- |
| NCM                    | 第一主力 provider | 优先接完整流媒体链路:播放、搜索、歌单、专辑、艺术家、歌词、评论、用户库、MV。 |
| QQ Music               | 第二在线 provider | 后续按同一领域端口接入,优先保证核心音乐能力一致,不追求官方客户端全功能。      |
| Local                  | 本地播放 provider | 扫描/导入本地音乐,读取元数据与本地歌词,提供本地库、搜索、播放与基础歌单能力。 |
| Preview-only providers | 实验/补充         | 如果只能提供试听或元数据,应明确标记为 preview 能力,不能伪装成完整 provider。  |

## 3. 要做的核心能力

### 3.1 播放与队列

必须做:

- 播放/暂停/上一首/下一首/seek/音量。
- 播放队列、顺序播放、随机播放、循环模式。
- 从歌单、专辑、艺术家热门、搜索结果、每日推荐等入口启动播放。
- provider 播放地址解析,支持全曲、试听、本地文件等不同播放来源。
- 播放失败时给出明确状态,不要静默失败或用假数据兜底。

暂不做:

- 下载器式的批量下载。
- 官方客户端式的复杂音效商城、会员音质营销入口。
- 多设备投放/接力播放,除非未来作为独立播放后端能力重新设计。

### 3.2 歌曲

必须做:

- 歌曲详情:标题、艺术家、专辑、封面、时长、平台 ID。
- 歌曲批量详情:用于队列、歌单、专辑等列表补全。
- 可播放性判断:能否播放、是否只有试听、是否需要登录或会员。
- 歌曲与 MV 的关联:如果 provider 提供 MV ID,应保留到领域模型中。

暂不做:

- 平台热度任务、听歌打卡、会员权益提醒。
- 复杂版权解释页。只需要用简洁状态表达不可播原因。

### 3.3 歌单

必须做:

- 推荐歌单/个性化歌单。
- 歌单详情与完整曲目列表。
- 用户创建/收藏的歌单读取。
- 歌单内播放、随机播放、加入队列。

可后置:

- 歌单创建、编辑、排序、删除。
- 收藏/取消收藏歌单。
- 歌单评论。

暂不做:

- 官方客户端的歌单运营活动、话题挑战、社交投稿。

### 3.4 专辑

必须做:

- 专辑详情:标题、艺术家、封面、发行信息、曲目列表。
- 专辑内播放、随机播放、加入队列。
- 从歌曲/艺术家/搜索结果跳转专辑。

可后置:

- 收藏专辑。
- 数字专辑购买入口。

暂不做:

- 付费购买、实体周边、粉丝运营相关页面。

### 3.5 艺术家

必须做:

- 艺术家详情:名称、头像/封面、简介。
- 艺术家热门歌曲,文案使用 `Hot` 或“热门”,不承诺固定数量。
- 艺术家专辑。
- 从歌曲/专辑/搜索结果跳转艺术家。

可后置:

- 相似艺术家。
- 艺术家 MV。

暂不做:

- 粉丝团、艺人动态、直播、应援、商城。

### 3.6 歌词

必须做:

- 歌词读取。
- 时间轴歌词滚动。
- 无歌词时展示明确空态。

可后置:

- 翻译歌词。
- 罗马音/音译。
- 本地 provider 的同名 `.lrc` 或内嵌歌词读取。

暂不做:

- K 歌、逐字卡拉 OK、打分、录音。

### 3.7 评论

必须做:

- 歌曲评论读取。
- 热门评论/最新评论的基础展示。
- 评论能力缺失时隐藏入口或展示空态。

可后置:

- MV 评论。
- 评论分页。

暂不做:

- 写评论、点赞评论、评论社交关系链。
- 私信、关注动态、用户争榜等社交功能。

### 3.8 搜索与发现

必须做:

- 搜索歌曲、歌单、专辑、艺术家。
- 搜索结果能直接播放或跳转详情。
- 榜单/推荐入口只展示可转化为播放体验的内容。
- 每日推荐、个性化推荐等 provider 支持时接入。

可后置:

- 搜索 MV。
- 高级筛选。

暂不做:

- 搜索播客、电台、动态、直播、用户广场。
- 热搜运营页里的活动、广告、挑战话题。

### 3.9 用户库与账号

必须做:

- provider 支持时接入登录状态。
- 喜欢歌曲读取与喜欢/取消喜欢。
- 用户歌单读取。
- 播放记录、每日推荐等与听歌强相关的个人能力。

Local provider 的对应能力:

- 本地音乐库索引。
- 本地歌单/收藏。
- 本地搜索。
- 本地歌词读取。

暂不做:

- 签到、积分、云贝、任务中心、会员成长体系。
- 云盘上传、云盘管理、跨端同步盘。
- 完整账号资料编辑、头像裁剪、隐私设置。

### 3.10 MV

可以做,但必须保持克制。

要做:

- 歌曲关联 MV。
- MV 详情与播放地址。
- 艺术家 MV 列表。
- MV 评论可以作为评论能力的延伸。

暂不做:

- 短视频流、Mlog、直播、视频社区、推荐信息流。
- 与音乐播放弱相关的泛娱乐视频。

---

## 4. 明确不做的能力

以下能力即使 NCM 或 QQ API 能拿到,也不进入 Planet 的核心范围:

- 签到、积分、任务、成长体系、会员营销。
- 播客、电台、广播、有声书、DJ 节目。
- 直播、K 歌、听歌房、一起听。
- 动态广场、关注流、粉丝团、私信、用户社交关系链。
- 云盘上传/管理、复杂同步盘。
- 商城、数字专辑购买、周边、票务。
- 官方客户端运营活动、挑战赛、话题页。
- 创作者后台、音乐人后台、数据看板。
- 广告、开屏、信息流推荐。

判断标准:如果一个能力不能直接增强“发现音乐、理解音乐、播放音乐、管理自己的音乐库”,默认不做。

## 5. 能力优先级

### P0: 先把 NCM 核心流媒体闭环做完整

- 搜索结果补齐歌单/专辑/艺术家入口。
- 歌曲详情与批量歌曲详情。
- 歌单详情与完整曲目。
- 专辑详情。
- 艺术家热门歌曲与专辑。
- 歌词读取与滚动。
- 歌曲评论。
- 喜欢歌曲、用户歌单、每日推荐、播放记录。
- 播放能力状态表达:全曲/试听/不可播。
- 文案诚实化,例如 `Top 50` 改为 `Hot`。

### P1: NCM 增强音乐媒体能力

- MV domain model 与 provider port。
- 歌曲关联 MV。
- MV 详情、播放、评论。
- 艺术家 MV。

### P2: 多 provider 横向扩展

- QQ Music 按 P0 能力逐项补齐。
- Local provider:本地扫描、元数据读取、播放、搜索、本地歌词、本地歌单。
- provider capability 矩阵可视化或调试面板,用于确认当前 provider 支持什么。

### P3: 体验深化

- 更稳的缓存策略。
- 大列表虚拟化与分页。
- 错误恢复与重试。
- 更细的 loading/empty/unavailable 状态。

---

## 6. 实现边界

新增能力时按这个顺序落地:

1. 先确认它属于本文的核心范围。
2. 在 `domain` 定义领域模型、端口和 capability。
3. 在 `providers` 做具体平台 mapper,屏蔽平台字段差异。
4. 在 `core` 或 application service 编排取数/播放/缓存。
5. 在 `ui` 展示能力,并根据 capability 隐藏不可用入口。

不要反过来从 UI 直接接接口。UI 可以推动需求,但接口形状必须沉淀到领域层。

新增 provider 时按同一标准验收:

- 是否能声明清楚支持/不支持的能力。
- 是否能把平台数据映射到统一 domain model。
- 是否能在缺失能力时保持 UI 可用。
- 是否能避免把平台专属概念泄漏到通用界面。

---

## 7. 文案约束

- 不承诺接口无法保证的数量。比如不要写 `Top 50`,写 `Hot` / “热门”。
- 不把不可用能力包装成可用。没有评论就是无评论/暂不可用,不是假评论。
- 不使用平台运营语言。Planet 的文案应服务于播放和浏览,不服务于促活。
- provider 名称可以出现于设置、调试、账号状态;普通音乐浏览页面尽量使用通用音乐语言。
