Sonance · Domain Model · v1

面向听众的模型,
不是面向唱片工业的模型。

主流播放器(网易云音乐 · QQ音乐 · Spotify · YouTube Music)对用户不暴露"词曲作品 / 录音版本 / 发行物"的学术三分。它们围绕一个能被点按、能进队列、能被红心的原子单位 —— 歌曲(Song)来组织一切。版权、词曲、编曲这些工业属性,降级为歌曲的字段,而非独立实体。下面是按这个心智重建的六层模型。

网易云音乐QQ 音乐SpotifyYouTube Music
学术 / 发行视角(弃用)
Composition 词曲作品
  └ Recording 录音版本
     └ Release 发行实体
        └ Track 曲目

三层引用链精确,但用户从不这样想。强行建模会让"点一下播放"跨越四个实体,交互全程绕路。

消费 / 人体工学视角(采用)
Song 歌曲  ←  原子单位
  ├ artists[]  主唱 + feat.
  ├ album     归属专辑
  ├ version   Live / Remix / 翻唱
  └ credits   词 / 曲 / 编(字段)

一个 Song 即可播放、入队、收藏、评论。"其他版本""作词作曲"是详情页里的字段,不是要先穿越的层级。

五条人体工学准则

模型为体验服务。下面是这套结构落到交互上的硬性约束。

01

一切皆可从 Song 起播

歌曲行、专辑卡、艺人头像、搜索结果、评论里被提到的歌 —— 用户点哪都应直接起播或入队,永不强制先进详情页。这要求 Song 自带足够展示字段(封面继承自专辑、艺人名串好)。

02

三种集合,视觉必须可辨

歌单 / 榜单 / 电台数据形状几乎一样,但歌单是策划、榜单是排名、电台是流。榜单要显名次与升降箭头,电台要显"无尽流 / 私人FM"标识,否则用户混淆。

03

分类是过滤器,不是目录树

语种 × 风格 × 场景 × 情感可叠加勾选,而不是层层下钻的菜单。浏览页用 chip 多选,搜索结果可按 facet 收窄。

04

队列必须记住"来源"

Playback.source 是"查看相似 / 跳回所在歌单 / 自动续播"的前提。旧模型把队列当裸数组,丢掉了 context —— 这是最容易忽视的体验断点。

05

会员 / 版权是一等状态

vipOnly 与 available 必须随 Song 一起到达每个渲染点,渲染前就知道能不能播,而不是点了才弹窗。置灰、角标、试听标记都依赖它。

落地建议

当前 data.jsx 是这套模型的扁平投影,三个界面都在跑。建议:保留现有导出形状,以向后兼容的方式补字段(见下表),而非推倒重写 —— 既对齐心智,又不破坏已有界面。

迁移映射 · 现有 → 新模型

把当前 src/data.jsx 平滑升级到该模型,绝大多数是"加字段",少数是"提升为实体"。
